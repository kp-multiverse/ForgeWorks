# ForgeWorks v3.0.0 -- Fable-era harness redesign

Date: 2026-07-25. Status: approved by owner (design review in session).
Supersedes the v2.x enforcement architecture. Breaking for generated projects (major version).

## Why (evidence, condensed)

Field evidence from the two v2.4.0 projects (heurema, kpakfar.me) plus a full harness
audit and current Anthropic guidance for Claude 5 models converged on four findings:

1. **Slow.** ~1 process/evidence commit per feature commit; one measured slice spent
   3.7h of 5.6h in memo/approval ceremony; the memo hard gate turned owner hesitation
   into a 3-week stall. Every subagent dispatch re-loads a ~9.4k-token constitution.
2. **Weak design output.** The gate chain proves function, never fidelity. Mockups are
   approved once then live untracked (`.local/mockups/`, claude.ai URLs). No design
   skill, no tokens, no screenshot verification. Result: "agents look dead" /
   zero-animation ships despite written aesthetic visions.
3. **Vision loss.** `PRODUCT_VISION.md` is read by nothing; subagents are told NOT to
   re-read docs; both projects built manual recovery ledgers. Harness gravity inverted
   the owner's "website first" priority into a month of invisible backend slices.
4. **Over-constraint.** 320 always-loaded lines, ~72 hard directives, key rules
   duplicated up to 5x. Matches Anthropic's published anti-pattern list for Claude 5
   models (they cut 80% of Claude Code's system prompt with no eval loss). The v2.x
   "more enforcement" remedies did not even achieve compliance (security-reviewer
   skipped, Red retroactive, task.md stale in a week).

Doctrine adopted (sources: Anthropic context-engineering post, Claude 5 new-rules post,
Claude Code best-practices docs, harness-design post, Fable field guide):
short factual core + progressive disclosure; prose is advisory, hooks/CI are
guarantees; ceremony tiered by risk and deletable; specs enforceable via tests and
machine-readable state, not prose; design needs tokens+mockup input AND a
screenshot-verifying evaluator; worker/judge separation; parallel agents only for
read-only work.

## Goals

- Cut the always-loaded constitution ~75-80% (320 -> ~70-90 lines).
- Move every procedure into on-demand skills.
- Replace prose/commit-choreography gates with deterministic checks.
- Make product vision survive into implementation via artifacts the loop must touch.
- Make design a first-class phase with a closed visual feedback loop.
- Human approval only where it pays: new user-visible surfaces, high-risk plans.

## Non-goals (YAGNI)

Image-model mockup generation; ralph-style outer-loop automation; new language
profiles; cross-agent adapter expansion beyond what v2.5.0 shipped; changes to
bootstrap/install.sh beyond version pins.

## 1. New `templates/core/AGENTS.md` (~70-90 lines)

Seven FW-BLOCKs (markers kept -- upgrade-project grafting depends on them), all v3.0.0:

| Block | Content |
|---|---|
| `project` | 2-3 lines: what this is + pointers to `docs/PRODUCT_VISION.md`, `docs/features.json`, `docs/design/DESIGN.md`, `docs/gotchas.md` |
| `commands` | qa/fix/e2e commands, toolchain facts the model cannot guess |
| `etiquette` | branch/PR conventions, Conventional Commits, one writer per branch |
| `hard-rules` | ONLY rules true 100% of the time: never weaken, skip, or delete a test to get green; never commit secrets; never flip a `features.json` status to `done` without its mapped tests passing; never delete `features.json` entries (mark `dropped` with a reason instead); security review fires on the trigger defined in the `security-review` skill |
| `risk-tiers` | the 3-row tier table (section 6) + "pick the tier by judgment against this table" |
| `learning` | 2 lines: add a `docs/gotchas.md` entry when reality surprises you; log implementation deviations in `docs/deviations.md` (conservative choice, log, keep going) |
| `roster` | one line per agent/skill: what exists and when to reach for it |

Deleted outright (content absorbed by skills or dropped): development-process,
architecture-discipline (top principles survive as ~3 lines inside the `slice` skill),
security-discipline (-> security-review skill), investigation-discipline,
token-discipline, test-discipline (-> slice skill / tdd skill), style-references
(A10 answer moves to `project` block as one line), design-discipline (-> design-loop
skill), global-documents, backlog-discipline, delivery-evidence,
task-specific-documents, library-docs, tools, quality-gate (hooks/CI are
self-describing), self-improvement (-> `learning`), agent-roster (-> `roster`),
recurring-reviews, loop-discipline, planning-discipline, exceptional-cases
(-> risk-tiers).

The conditional `ai-discipline.md` block is rewritten to <=8 lines (LLM I/O boundary
handling, prompt changes are behavior changes, fakes keyed off rendered state) and
still renders only when B4 selects an AI feature.

## 2. Procedures -> generated skills (`templates/core/.claude/skills/`)

All terse, imperative, <150 lines each; reference files only where needed.

- **`slice`** -- the per-slice workflow. Steps: read the feature's `features.json`
  entry (including `serves:`); pick tier; standard tier = short plan (free-form, no
  heading floor) -> Red -> Green -> scoped code review -> design review if
  user-visible -> update `features.json` status + tests mapping; high-risk tier adds
  user-approved plan (committed to `docs/plans/<feature-id>.md`) and security review.
  Carries the surviving architecture principles (~3 lines: two-layer split, small
  focused files, no premature abstraction) and the probe guidance (record probes for
  flaky/undocumented external collaborators; stable documented APIs may be coded
  against their docs).
- **`design-loop`** -- section 5.
- **`security-review`** -- the canonical 6-clause trigger lives HERE, once (its 5
  verbatim copies across v2 files are removed). Procedure: when the trigger matches,
  dispatch `@security-reviewer`, apply the SECURITY.md delta or record "none,
  because".
- **`tech-debt`** -- on-demand sweep (was an every-3rd-slice mandate + agent; the
  agent file is deleted, the skill dispatches a general-purpose review with the same
  checklist).
- **`select-agents`** -- unchanged from v2.5.0.

Phase 1 installed skills (tdd, grill-me, to-prd, caveman, write-a-skill, handoff)
are kept; tdd and grill-me are invoked by tier (standard+ for tdd, high-risk or
on-request for grill-me), not universally.

## 3. Deterministic gates replace prose gates

**Removed:** memo->Red->Green commit-ancestry CI check; `slice-audit.sh` PreToolUse
hook; 11-field ship records + `docs/ships/`; the 9-heading memo floor + `docs/designs/`
memo library; the 88-line `docs/current-task/task-template.md` ritual and
`docs/current-task/` entirely; `docs/backlog.md`; `docs/requirements.md`;
`docs/structure.txt` (directory trees are exactly what /doctor deletes as cruft --
the CC-TREE fence family goes with it).

**Kept:** QA Stop hook, `deps-guard.sh`, profile CI quality gates -- already
deterministic and cheap.

**Added:**

- **`docs/features.json`** -- the enforceable spec and single source of feature truth
  (replaces requirements.md REQ table + backlog.md). Schema:

  ```json
  { "features": [ {
      "id": "F001",
      "title": "",
      "intent": "one line",
      "serves": "which vision differentiator / journey step",
      "acceptance": ["..."],
      "tests": ["path::test_name"],
      "status": "todo | in-progress | done | dropped",
      "tier": "light | standard | high-risk",
      "notes": ""
  } ] }
  ```

  Ordering in the array IS priority order. The interview seeds it (section 4).
  A new CI job `features-check` (stdlib Python script in the generated repo,
  `scripts`/package parity per profile) validates: schema; every `done` feature has
  >=1 `tests` entry whose file exists; `dropped` requires a non-empty `notes`.
  Execution of those tests is the existing QA gate's job, not this check's.
- **`docs/deviations.md`** -- append-only log; seeded with a 3-line header explaining
  the convention.
- **`docs/plans/`** -- exists for high-risk tier plans only; README of 5 lines.

## 4. Vision pipeline

- Interview answers compile into three artifacts the loop must touch:
  `PRODUCT_VISION.md` (short: positioning, differentiator, success metrics),
  `features.json` (core journey decomposed into ordered features with `serves:`
  lines -- the interview's Phase 3 plan summary already produces this decomposition;
  Phase 4 now writes it into the answers file and render.py emits it), and
  `DESIGN.md` (section 5).
- The `slice` skill's first step reads the feature entry; subagent briefs include the
  feature entry + mockup path. All "do not re-read the full doc set" walls are
  removed from agent files.
- **Ordering rule** (lives in the `slice` skill, one line): user-visible journey
  features lead the array unless the owner reorders; hardening/infra features queue
  behind the first shippable surface. (Direct fix for the kpakfar.me inversion.)

## 5. Design phase (full loop)

- **Interview**: two new questions, asked only when the project has a UI
  (`HAS_FRONTEND`): **V1** -- 2-3 visual references (real sites/products) + what
  specifically to take from each; **V2** -- 3 tone words + one anti-reference
  ("never make it look like ..."). A10 (codebase-shape reference) is unchanged and
  now clearly labeled as code style, not visual style.
- **Generated files**:
  - `docs/design/DESIGN.md` -- direction (from V1/V2), token rationale, and a written
    **aesthetic rubric** the design reviewer grades against. The rubric names and
    bans generic-AI tells (purple-gradient hero, three-rounded-cards grid, default
    Inter everywhere, uniform border-radius soup) and requires one justified
    aesthetic risk per surface. V1/V2 answers are substituted; the rubric text is
    canonical template text.
  - `docs/design/mockups/` -- committed mockups, named `<feature-id>-<name>.html`.
    **The approved mockup is the spec for that surface.** README of 6 lines.
  - A design-tokens file, emitted iff `HAS_FRONTEND` (TS: `src/styles/tokens.css`;
    Python: `static/tokens.css`; Go/Rust: no tokens file in v3.0.0 -- their profiles
    have no web scaffold) seeded from V1/V2 palette/tone hints with TODO markers.
- **`@design-reviewer`** (new agent, `templates/core/.claude/agents/design-reviewer.md`,
  <=60 lines): after a user-visible slice is green, open the running app with
  available browser tooling, screenshot the changed surfaces, grade against the
  approved mockup + DESIGN.md rubric, report only fidelity/rubric gaps. If no
  browser tooling is available, it says so and grades statically (markup/styles vs
  mockup) -- it never silently passes.
- **`design-loop` skill**: new surface -> produce 3-4 genuinely divergent directions
  as throwaway HTML -> owner picks (the ONE mockup approval gate) -> commit winning
  mockup to `docs/design/mockups/` -> build -> screenshot-compare vs mockup + rubric
  -> iterate until the design reviewer passes or the owner accepts deltas (logged in
  deviations.md).
- Conditional emission: the whole `docs/design/` tree + design-reviewer agent +
  design-loop skill ship only when `HAS_FRONTEND` (new render.py skip rule; both
  states covered in golden fixtures).

## 6. Risk tiers and human gates

| Tier | Examples | Ceremony |
|---|---|---|
| **light** | copy, styling tweaks, small fixes, internal refactors | build + QA green |
| **standard** | new feature/behavior | short free-form plan, Red->Green, code review (correctness + requirements only), design review if user-visible |
| **high-risk** | auth, payments, security trigger, architecture change | owner-approved plan in `docs/plans/` + security review + full test pyramid |

Human approval exists in exactly two places: mockup pick for a NEW user-visible
surface, and high-risk plans. Everything else proceeds; deviations are logged; the
owner reviews diffs. There is no "lean directives may not waive" language anywhere --
tier choice is judgment, and the deterministic gates (QA hook, features-check,
deps-guard) are the floor that cannot be waived because they are machines.

## 7. Agent roster changes

- **Keep**: `implementer` (rewritten <=40 lines: brief = feature entry + plan if any
  + mockup path; memo-refusal clause removed -- it requires an approved plan only for
  high-risk tier), `code-reviewer` (rewritten <=40 lines: correctness + requirements
  coverage only, per the official "gap-hunting reviewers cause over-engineering"
  caveat), `security-reviewer` (kept, trigger text replaced by a pointer to the
  security-review skill), `utility` (unchanged), `design-reviewer` (new).
- **Delete**: `test-spec-writer` (test-naming guidance folds into the slice skill's
  Red step), `tech-debt` agent (replaced by the tech-debt skill).
- AI-IMPL / AI-REVIEW fenced sections survive in the rewritten agent files (slimmed);
  fences stay registered in upgrade-project Phase 3-A.

## Risks / accepted trade-offs

- The v2.1 provable-history audit trail is removed. Accepted: it demonstrably failed
  its purpose in the field while costing ~half of commit traffic; features.json +
  deterministic gates + owner diff review carry the risk instead.
- Old projects need the migration to benefit; until run, they keep working on v2
  semantics (upgrade reconciles by capability detection, not version).
- The design loop depends on browser tooling availability at project runtime; the
  reviewer degrades to static grading, never silent passes.
