# ForgeWorks v4.0.0 — the software factory (design)

Date: 2026-08-01
Status: approved by owner (section-by-section, this session)
Release: v4.0.0 (breaking for generated projects)

## Why

Two independent reviews of v3.0.0 (Fable 5 + Codex CLI 0.144.1, 2026-08-01), run after
the heurema field deployment, converged on the same diagnosis:

1. **No visible path between agents.** The pipeline exists only as prose scattered
   across `AGENTS.md`, `slice`, `design-loop`, and four agent files. `slice` never
   explicitly dispatches `@implementer`; there is no merge procedure at all; nothing
   at runtime records which agent is active or which round it is on.
2. **Unbounded loops by construction.** `design-loop` step 5 says "iterate until it
   reports MATCHES" with no cap. `slice` requires reviews "resolved" with no cap on
   rounds, and each round spawned a fresh reviewer that re-read the whole project
   (7–21M cache tokens per re-review, measured). The implementer had no turn cap
   (one ran 1,100+ turns). The reviewer Stop hook blocks on red QA — a gate, not a
   termination policy.
3. **Default-on ceremony.** A standard visible slice could involve seven artifacts and
   four subagents. Multi-agent choreography was the default, not an earned escalation.
4. **Litter.** Nothing cleaned up worktrees after merge: heurema left ~10.5 GB of
   stale worktrees, several holding unmerged branches — slices started, never landed.

Verdict (both reviewers): salvage the discipline, scrap the choreography. v4.0.0 is a
**simplification release**: it removes defaults instead of adding rules.

**Field benchmark (2026-08-01).** Three research passes (vendor guidance: Anthropic
Claude Code best practices + engineering blogs, OpenAI Codex docs; framework survey:
Spec Kit, Kiro, BMAD, Agent OS, superpowers, OpenSpec, GSD, Ralph; practitioner
economics: Ronacher, Beck, Willison, Cross-Context Review arXiv 2603.12123, Context
Rot) confirmed the loop shape matches the 2026 consensus — gate the design hard,
build with automated backpressure, one fresh-context review, caps not trust — and
contributed the eight adopted amendments marked "(research)" below. Consciously
rejected: multi-persona rosters (BMAD-style), always-on mutation testing, unattended
Ralph-loops (greenfield-only, endemic false "done" claims).

## Goal

A software factory for a solo owner: describe what you want, approve a grilled design,
get proper reviewed software merged back — no repetition, no unbounded loops, no
ceremony that does not pay for itself, and a path you can watch.

## Non-goals

- No new generator machinery. `render.py`, the answers-file contract, language
  profiles, and golden-fixture CI stay (extended, not replaced).
- No change to heurema in this release. Migration happens after the v4.0.0 tag via
  `upgrade-project`.
- No "Other" language profile work.

## Owner decisions (recorded)

- Default build mode: **solo** — the main agent implements. Multi-agent is proposed
  by the system only when genuinely warranted, and the owner approves the proposal.
- Bootstrap: **conversation, ≤5 questions**; everything else defaults.
- Grilling: **every real feature**; chores skip it. Two tiers total.
- **Security is a design input**: threat-modeled at GRILL, not discovered at REVIEW
  "with 100 diff problems."
- Approach: **new harness on the proven engine** (not clean-slate, not additive patch).
- Three gaps from heurema, closed by design (owner, mid-session): decisions made in
  conversation must be written down and enforced; the owner must be able to see what
  the final product looks like (PRD + readable backlog); mockups must be mechanically
  unskippable.
- Context is a managed budget (owner, spec review): the main agent is the context
  orchestrator — minimal dispatch briefs for every subagent, one always-loaded file
  only, doc shrinking enforced at MERGE (Section 4).

## 1. The iteration loop

One skill, **`iteration`**, replaces `slice` + `design-loop` dispatch prose. It is the
only per-feature workflow. Two tiers:

**Chore** — typo, copy, small fix, refactor with no behavior change: build → quality
gate green → commit. No feature entry, no review round, no ledger ceremony beyond the
commit itself.

**Feature** — anything with new or changed behavior:

```
GRILL → RED → GREEN ──QA gate──→ REVIEW ──QA gate──→ MERGE ──QA + e2e + features_check──→ done
  │                                  │
  security designed here     security verified here
```

### GRILL (design + the one human gate)

The agent drafts a short plan: approach, riskiest bit, data shapes at boundaries,
test list mapped to acceptance criteria. **Acceptance criteria are written in EARS
form (research)** — `WHEN <condition> THE SYSTEM SHALL <behavior>` — so each criterion
converts 1:1 into a RED test name and `features_check.py` can mechanically verify
every criterion has its test. For a new visual surface, 3–4 divergent
mockups are part of the plan (the design-loop diverge/owner-pick step survives here).
Then the agent **attacks its own plan** — strongest objections, failure modes, simpler
alternatives — and presents plan + objections + resolutions to the owner.

**Security at design time.** The plan always answers one standing question: "does this
touch the trigger list?" (auth, payments, new input surfaces, secrets, new
dependencies, LLM-facing text). If yes, the plan must contain a **mini threat model**
as a first-class section: the new attack surface, who can send what through it, where
each input is validated (allowlist at the boundary, fail closed), behavior when the
external world misbehaves, and what an attacker tries first. The self-grilling must
include the attacker's perspective ("how would I abuse this?") among its objections.
The threat model asks one standing structural question — the **Rule of Two
(research)**: does this feature combine untrusted input + sensitive data + external
write/egress? If all three, redesign to drop one leg or put a human approval on the
action. Security tests named here become RED tests like any other.

**Fan-out proposal (solo is the default).** The plan answers a second standing
question: "can this split into independent pieces touching disjoint files?" Only when
genuinely yes (≥2 pieces, no shared files, no ordering) may the plan include a fan-out
proposal: how many parallel agents (**never more than 5 — the field's human-review-
bottleneck ceiling (research)**), what each does, expected benefit, and a cost note
("~N× tokens of a solo build"). Overlapping files, unclear boundaries, or "might be
faster" are explicitly not reasons. The owner approves fan-out as part of the normal
GRILL approval — no extra gate.

**Decisions are written, not remembered.** GRILL is not finished until the approved
plan is written to `docs/plans/<feature-id>.md` — for **every** feature, not just
high-risk work. The plan file records: what the owner asked in their own words, every
decision made in the conversation (including explicit "owner said no to X" lines),
the threat model when triggered, the fan-out decision, and the final test list. The
feature's acceptance criteria in `features.json` are updated to match before RED
starts. A decision that lives only in chat does not exist.

**The plan file is a self-contained carrier (research).** It must hold everything a
*fresh* session needs to execute the feature (files to touch, interfaces, out-of-scope
lines, the EARS criteria) and fit comfortably in half a context window. Between
features the driver clears context; the plan file, `features.json`, and the ledger are
the memory — never the conversation. This is the field's strongest anti-token-burn
pattern (stateless sessions + files-as-state).

**Mockup gate (mechanical).** Every feature entry carries a `surface` field — the
screen/surface it touches, or `none`. If `surface` is set and no approved mockup
exists in `docs/design/mockups/`, the feature **cannot leave GRILL**:
`features_check.py` enforces it (a `surface` feature may not leave `status: todo`
without an existing mockup path in its entry), independent of agent goodwill. New surface → mockups diverge and the
owner picks at GRILL; changed surface → its mockup is updated in the same branch.

Owner approves once, here. This is the only routine human interruption.

### RED

Failing tests first, mapped to the acceptance criteria (including the security tests
named at GRILL). Feature's `tests` array updated as they are named.

### GREEN

The **main agent implements in the main context**. No implementer subagent by
default. If fan-out was approved: each parallel agent gets a worktree, per-agent caps
apply, and all results converge into the single REVIEW below. Exit condition: the
full quality gate (lint, format, types, unit + functional) is green. A red gate
cannot enter REVIEW.

### REVIEW (one round, wider lens)

One fresh-context `@reviewer` pass covering, in one round:

- **Correctness + requirements** (the current code-reviewer scope: every acceptance
  criterion maps to a real test; unexplained test/fixture/gate changes are findings).
- **Plan conformance**: the diff is checked against `docs/plans/<feature-id>.md` —
  drift from what the owner decided at GRILL is a **blocking finding**, not a
  post-merge surprise. Deliberate deviations must already be in `docs/deviations.md`.
- **Design fidelity** when the diff touches a visual surface: grade against the
  committed mockup + rubric (absorbs `@design-reviewer`).
- **Security** when the trigger matched: run the `docs/SECURITY.md` red-team
  checklist against the diff and verify the threat model's tests exist and pass
  (absorbs `@security-reviewer`). A triggered feature cannot merge without this.

**Finding triage (research).** Any finding not tied to a failing check, an EARS
criterion, or the plan file is marked *optional* and never auto-fixed — a reviewer
prompted to find gaps always finds some, and chasing them is the over-engineering
loop. Blocking findings require evidence (the failing test, the violated criterion,
the plan line). Fresh context for round one; the single permitted re-review continues
the same conversation (a second fresh pass measurably performs worse).

The reviewer reads the **diff plus grep-targeted doc sections only** — whole-file
reads of docs >30K chars are forbidden in its prompt. Its Stop hook re-runs the
quality gate and blocks APPROVE while red (kept from v3).

### MERGE (explicit, scripted)

Gate + e2e suite + `features_check.py` green on the merge result → merge to main →
**delete the branch and every worktree the feature created** → set feature status →
**move the plan file to `docs/plans/archive/` (research: archive-on-merge — living
docs stay small, the audit trail stays complete)** → regenerate `docs/BACKLOG.md`
from `features.json` → append the ledger line. Merge is a defined step in the skill
with its own checklist, not an afterthought.

### Hard caps (the termination policy)

| Cap | Limit | On hit |
|---|---|---|
| Fix passes after REQUEST_CHANGES | 2 | stop, ask owner |
| Re-reviews | 1 — and it **continues the same reviewer conversation**, never a fresh spawn | stop, ask owner |
| Design reworks (mockup fidelity) | 1 | stop, ask owner with named deltas |
| GREEN stall | 2 consecutive failed test cycles on the same failure | checkpoint commit + stop, ask owner — the recommended recovery is a fresh context re-primed from the plan file with the failure lesson added, not more turns in the stuck session (research) |

"Stop, ask owner" means: one-paragraph status (state, rounds used, what is stuck,
the agent's recommendation) and no further spend until the owner answers.

### The ledger

`docs/LEDGER.md`, one line appended at every state change:

```
F012 | GREEN | round 1/2 | 2026-08-01 14:02 | agent: main | gate: 42 passed
F012 | REVIEW | round 1/1 | 2026-08-01 14:31 | agent: reviewer | APPROVE, 1 optional
F012 | MERGED | 14:58 | worktrees: 0 remaining | e2e: 7 passed
```

**Evidence, not assertions (research):** every ledger line carries its proof — test
counts, the command run, screenshot paths for visual checks. A state change without
evidence is invalid; "looks done" is never a stop signal.

At any moment the owner opens one file and sees where the factory is, what round
anything is on, and that cleanup happened. This is what makes agent paths visible.

## 2. The roster

**Two contexts in the critical path:**

- **Main agent** — foreman and builder: grills, writes tests, implements, merges,
  keeps the ledger.
- **`@reviewer`** — one fresh-context subagent per feature carrying the merged lens
  above. Fresh context is the point: the builder never grades its own work.

`@utility` (haiku, mechanical chores) stays available, never in the critical path.

**Removed from the default path:** `@implementer`, `@design-reviewer`,
`@security-reviewer` (agent files deleted; their checklists live in the `@reviewer`
prompt and the `iteration`/`security-review` skills), the `select-agents` skill
(roster changes become a documented manual edit of `docs/agents.json`), and the
three-tier risk table (two tiers inside `iteration`).

**Cleanup guarantee:** MERGE deletes the feature's worktrees; additionally the
generated project ships a `factory doctor` one-liner (documented in AGENTS.md
commands) that lists and prunes stale worktrees and merged branches. The heurema
folder mess becomes structurally impossible.

**Cross-agent parity:** on non-Claude rosters the same states apply; subagent passes
become independent fresh-context passes, as today. The skills define what each state
checks, so the loop is driver-agnostic.

## 3. Conversational bootstrap

`/init-project` becomes: the owner describes the product in one message; the agent
infers what it can and asks **at most five questions**, only where inference failed
or stakes are high:

1. What & for whom (asked only if missing from the description)
2. Language (inferred when obvious; Python / TypeScript / Go / Rust)
3. Frontend? (+ one visual reference like/hate follow-up if yes)
4. Anything security-sensitive? (real user data, payments, auth, external input)
5. Which agents drive (Claude Code only vs. + Codex — B13 survives as one question)

Everything else (devcontainer, memory, explanations, gotchas seed, and the rest of
today's B-questions) becomes defaults written into the answers file, each changeable
later. The agent shows a five-line summary; on OK it writes the same answers-file
schema and runs `render.py` unchanged in role: same deterministic bytes, same golden
fixtures proving it. The interview is the only thing that changed — from a form the
owner fills to a conversation that fills the form.

**The product picture (PRD + readable backlog).** The bootstrap conversation ends by
producing a one-page **`docs/PRD.md`** the owner approves before anything is built:
the end-to-end user journey, the list of screens/surfaces, and an explicit
"v1 includes / v1 excludes" line. Every feature's `serves:` points at it (it absorbs
today's PRODUCT_VISION.md role as the concrete picture of the finished product).
`features.json` stays the machine spec, but `scripts/backlog.py` regenerates
**`docs/BACKLOG.md`** at every MERGE — an ordered human-readable list (done / in
progress / todo, one line each) — so the owner always sees where the product stands
without reading JSON.

**Doc budgets (from the heurema audit + research):** generated docs carry per-doc
character budgets — SECURITY.md ~20K, gotchas.md ~15K, deviations.md ~10K — with
overflow archived to `docs/archive/` in the same PR that grew them. The generated
**AGENTS.md itself holds a hard ≤100-line budget** (instruction files past ~1,000
words measurably degrade agent compliance); sometimes-relevant content goes to
on-demand skills, lint/format rules stay in CI and never in prose. Enforced by a rule
in the core AGENTS.md and (optionally) a CI `docs-budget` job beside `features-check`.

## 4. Context economy (the orchestrator's contract)

The heurema failure to never repeat: always-loaded docs ballooned (SECURITY.md hit
159K chars, injected into every call) and every fresh subagent re-read the project
(7–21M cache tokens per re-review). v4 makes context a managed budget with the main
agent as **context orchestrator** — paying attention to what every call carries is
its explicit job, not a side effect.

**Always-loaded set is enumerated and closed.** Exactly one file loads on every call:
the generated AGENTS.md, hard-capped at 100 lines. Nothing else is always-on.
PRD, SECURITY.md, gotchas, design docs, standards — all on-demand, reached through
the skills or grep-targeted reads.

**Dispatch briefs, not "read the docs."** Every subagent dispatch (reviewer or
approved fan-out) is composed by the orchestrator as a minimal brief: the plan file,
the diff (or file list), the specific doc *sections* it needs (grep-targeted), the
mockup path if visual. The brief names exactly what the subagent may read; whole-file
reads of any doc >30K chars are forbidden in every subagent prompt, not just the
reviewer's. Subagents return condensed results (~1-2K tokens: verdict + findings +
evidence), never transcripts.

**Doc lifecycle is enforced at MERGE.** The merge checklist includes a doc-size
check: any budgeted doc over its cap gets its overflow archived to `docs/archive/`
in the same PR — shrinking is part of shipping, not a someday chore. `docs/LEDGER.md`
rotates the same way: completed features' lines move to `docs/archive/LEDGER-<year>.md`
when the live file passes ~10K chars, keeping the always-glanceable file small.
`docs/BACKLOG.md` is bounded by construction (one line per feature). The optional CI
`docs-budget` job fails the build when a budgeted doc is over cap, so drift cannot
merge silently.

**Session hygiene.** One feature per session; context cleared between features; the
plan file + features.json + ledger are the memory across sessions (Section 1). The
orchestrator never pastes doc content into a brief that the subagent could grep for
itself in one targeted read.

## 5. Delete / keep / new (file level)

**Deleted or absorbed** (generated tree):
- `.claude/skills/slice/`, `.claude/skills/design-loop/`, `.claude/skills/select-agents/`
  → one `.claude/skills/iteration/`
- `.claude/agents/implementer.md`, `design-reviewer.md`, `security-reviewer.md`
  → `.claude/agents/reviewer.md`
- Three-tier risk table in AGENTS.md → two tiers in `iteration`
- The A1–A10/V1–V2/B1–B13 interview → the Section 3 conversation
- `docs/PRODUCT_VISION.md` → `docs/PRD.md` (the concrete product picture replaces it;
  positioning/differentiator content folds into the PRD's one page)

**Stays (proven, load-bearing):** `bootstrap/install.sh`; `render.py` + answers-file
schema (extended: new defaults section, new placeholder set); all four language
profiles; golden-fixture CI (fixtures regenerated for the new tree); `upgrade-project`
(updated to graft v4 blocks — heurema's migration path); `quality-gate.sh` +
`deps-guard.sh` hooks; `features.json` + `features_check.py`; `docs/SECURITY.md`
(trimmed to budget); `docs/design/` (tokens, rubric, mockups — frontend-only,
conditional as today); `tech-debt` skill; `@utility`; `.mcp.json`; CI shape.

**New:** `iteration` skill; `reviewer.md`; `docs/LEDGER.md` (+ ledger rule);
`docs/PRD.md` (bootstrap-produced, owner-approved); `docs/BACKLOG.md` +
`scripts/backlog.py`; per-feature plan files in `docs/plans/` (every feature, decision
record format); `surface` field in the `features.json` schema + its mockup gate in
`features_check.py`; `factory doctor` one-liner; doc-budget rule; threat-model section
in the GRILL plan format (incl. Rule of Two); fan-out proposal format (≤5 agents);
**test-tamper guard (research)** — a CI/hook check flagging any modified or deleted
existing test without a stated reason in the commit or review notes, giving the
"never weaken a test" hard rule mechanical teeth; `docs/plans/archive/`.

AGENTS.md FW-BLOCKs are rewritten accordingly (all bumped to v4.0.0); `upgrade-project`
Phase 3 registers the removed/renamed files so migration reports them correctly.

## 6. Acceptance (how we prove it before tagging)

1. `golden_test.py` green: fixtures regenerated for the v4 tree, byte-for-byte.
2. Root CI green: every profile renders with no leftover placeholders; each profile's
   quality gate passes on the merged core+profile tree; deps-guard exercised; the
   rendered AGENTS.md is ≤100 lines and every budgeted doc starts under its cap.
3. **One live factory run:** bootstrap a throwaway project (`BRANCH=<this branch>`),
   confirm the conversation produces an owner-approved `docs/PRD.md`, then run one
   real feature through the full loop — grill (with a security-triggered plan written
   to `docs/plans/`), red, green, review, merge — and verify: plan file records the
   decisions with EARS criteria, mockup gate blocks a `surface` feature without a
   mockup, ledger lines carry evidence, caps respected, test-tamper guard fires on a
   deliberate test edit without a reason, plan archived and `docs/BACKLOG.md`
   regenerated at merge, branch and worktree gone, gate green throughout.
4. Then: PR → main → tag v4.0.0 → re-pin per `<release-process>`.

Heurema migration is explicitly after the tag.
