# v4.4 -- the dispatch economy (multi-agent strategy, priced)

Status: DRAFT -- awaiting owner GRILL decisions (numbered below).
Depends on: v4.3 (mechanical doc death) merged first.

## The problem, from the field

v4 has multi-agent *moments* (reviewer, utility, an unused fan-out clause) but
no strategy: no rule for when work leaves main context, no model policy, no way
to run two features at once. Meanwhile the owner's diagnosis stands: the v3
choreography burned tokens without provable speed (1000-turn implementers,
re-reviews re-reading everything, 12 stale worktrees, writers sharing an
index). Any new strategy must optimise cost/speed, not head-count.

## The two principles everything below derives from

**P1 -- A fresh agent is cheap by construction.** A subagent's cost is its
brief plus its work; it never pays for the conversation's history. So the unit
of dispatch is a JOB CARD small enough that a fresh context can execute it
alone -- the same fresh-session test the plan cap already enforces.

**P2 -- The cheapest model whose failure the gate would catch.** Model choice
keys to how the output is VERIFIED, not to how hard the work feels:

- Output verified mechanically (failing tests to make pass, a schema to fill,
  a command whose exit code decides)? A cheap/fast model -- a wrong answer
  fails loudly and costs one retry.
- Output verified by judgment (a plan, a test's assertions, a review verdict,
  a threat model, a mockup)? The top model -- wrongness here is silent and
  compounds.

Corollary: RED is judgment (the tests ARE the spec -- top model writes them);
GREEN against those tests is mechanical enough for the mid tier; REVIEW is
judgment again. The gate, not the model, is the quality floor.

## What ships

### 1. The model ladder (roster-neutral)

Three named tiers in `docs/agents.json`, mapped per harness at init/upgrade:

    "model_tiers": { "mechanical": "<cheap>", "standard": "<mid>", "judgment": "<top>" }

Core prose refers only to tier names; concrete model ids live in agents.json
(Claude roster default: haiku / sonnet / the session's top model). Every
dispatch names its tier explicitly -- field gotcha: an unpinned subagent
inherits an expensive default silently.

### 2. Job cards

A dispatch is a job card (in the plan's Fan-out section, or inline for
chores): deliverable shape, exact inputs (paths + sections, never "read the
docs"), tier, done-check (the command or test that verifies it), and a token
note. If a card cannot be written that small, the job is not dispatchable --
main context keeps it. Cards replace the current free-prose "minimal brief"
rule with a checkable shape.

### 3. The dispatch policy (one rule, in the iteration skill)

Work leaves main context only when BOTH: (a) its done-check is mechanical, or
it needs fresh-context independence (review); and (b) a job card fits. Routing:

- mechanical tier: chores with a done-check (renames, regenerations, log
  mining, prune/backlog runs, dep bumps that the gate verifies).
- standard tier: GREEN for a feature whose RED tests are complete and green-on
  -pass is the whole contract; also golden-path e2e authoring from an approved
  spec.
- judgment tier (or main context): GRILL, RED, REVIEW, security lens, any
  design/mockup work, anything whose card cannot name a done-check.

### 4. Batch mode -- cross-feature parallelism (the speed half)

At GRILL the owner may approve a BATCH: 2-4 features whose files are disjoint
(proven by the plans' files-to-touch lists intersecting empty). Each feature
gets its own worktree, branch, and single writer -- commits before any
dispatch (the stash field bug). Merge is a queue, one at a time, full gate per
merge; `factory_doctor.sh` asserts zero worktrees after the batch. The ledger
carries one line per feature per state, same caps -- nothing new to write.
Batch mode is FULL-weight only (below) and never implicit.

### 5. Project weight (the profitability half)

One question at init (changeable in agents.json): `weight: lite | full`.

- **lite** (solo site/tool): solo + `@reviewer` only; no batch mode; Codex
  second opinion off by default; e2e at release, not per feature; dup gate
  advisory. The factory a one-person project can afford.
- **full**: everything above available; review scaled to risk as today.

### 6. The meter (make cost visible, mechanically)

`factory_doctor.sh` gains a report line computed from git alone: docs:code
commit ratio and features merged per week. No new doc, no agent writing -- the
poison metric the owner found by hand becomes a number the doctor prints.

## Explicitly out of scope

No new subagent files beyond reviewer/utility (tiers are dispatch parameters,
not roles); no orchestrator agent; no per-job cost ledger lines (v4.3 just
shrank the ledger); no Claude-only mechanics in core (tier names are neutral,
mappings live in agents.json; anything harness-specific goes behind a CC
fence).
